Un dépôt MuleSoft ne produit aucun graphe utile : sa logique vit dans `src/main/mule/**/*.xml`, que CodeGraph n'extrait pas (ni XML ni Mule parmi les langages de la 1.6.2, dernière publiée au 14/10/2026). Besoin constaté sur une application d'intégration réelle.

Précédent dans le dépôt : `pipeline/flows.py` (phase 4) parse les `.flow-meta.xml` Salesforce avec `xml.etree` et ajoute des arêtes `calls`/`imports` ; no-op sans fichier concerné. Même schéma pour Mule :

- nœuds : `flow`, `sub-flow` ; points d'entrée = sources (`http:listener` et son `path`, listeners de connecteurs, `scheduler`) ;
- arêtes : `flow-ref` → `calls` ; `http:request` (config et `path`) vers les API appelées ; gestionnaires `on-error-*` par type d'erreur ;
- propriétés `${…}` et `p('…')` référencées, utiles au drill-down ; DataWeave inline lisible par `enrich.py`.

Critère : sur un dépôt Mule 4 réel, chaque flow et sub-flow est un nœud, chaque `flow-ref` une arête, les points d'entrée HTTP apparaissent ; no-op sur un dépôt sans XML Mule ; tests unitaires comme pour `flows.py`.

Piste CodeGraph : si l'extraction passe par un fork de CodeGraph plutôt que par une phase Python, partir de la **dernière version publiée** (`@colbymchenry/codegraph` 1.6.2 au 14/10/2026), pas de la 1.6.0 installée ni de `CODEGRAPH_TESTED_VERSION` (1.5.0). Même arbitrage pour le SQL : [[T-002]].
